# MVP 文件存储设计

状态：经评审的存储设计，已提交实现；真实 OSS 和容器环境的验收状态见 [验证记录](../validation/task-090.md)。更新日期：2026-09-23。

## 1. 范围

一期只使用本地文件或阿里云 OSS 中的一种正文存储。每篇笔记只有当前内容，不做搜索、持久化或全库笔记索引、备份、历史副本或归档。允许按访问建立的有界进程内校验缓存，不保存全库目录或用于搜索。

浏览器 IndexedDB 只保存当前草稿与待提交状态，不增加服务端数据库依赖。应用运行在一个活动 Node.js 实例中，所有设备经该实例读写。

## 2. 正文格式

推荐直接保存 UTF-8 Markdown 文件：内容是用户写下的文字，以及标题、列表、加粗等内容格式的 Markdown 标记。界面样式、主题和编辑器 UI 状态由 Web 端负责。Markdown 是本提案的推荐格式，用户已明确的要求是只保存笔记内容，不存页面 HTML 和样式。

```text
notes/
  <note-id>.md
```

文件只包含笔记内容，不加 HTML 页面、CSS、JSON 外壳、front matter 或隐藏的提交标记。标题从首个非空内容行派生，完整内容一起保存。文件名由稳定 ID 决定，修改内容或标题不改路径。

列表仅读取文件的有界开头片段（建议最多 8 KiB）提取标题；显示时可去掉 Markdown 标记并截断，但不改写原文。片段内没有可用内容时显示“未命名笔记”。正文原型先以 1 MiB 测试边界，不为列表读取整篇正文。

编辑器显示为可视化富文本，保存时转换成 Markdown，打开时从 Markdown 恢复；用户不必手写标记。Tiptap 官方 Markdown 扩展当前为 Beta，需验证其具体版本与一期功能的兼容性。编辑器运行时的内部模型不写入文件，Markdown 解析与转换的开销仍须计入启动预算。[Tiptap Markdown 文档](https://tiptap.dev/docs/editor/markdown)。

一期仅提供约定 Markdown 能表达的编辑功能，任务列表使用常见的任务项扩展语法。验证标题、列表、强调、任务状态、链接、代码块、中文和换行的往返；连续空段落等未必能被标准 Markdown 无损表达的结构须明确约定编辑行为，不能默认支持所有富文本结构。遇到不支持的内容保留原文和草稿，不能静默丢失。

服务端按文件字节读写，不为了存储把正文转成 JSON 或 HTML。通过认证接口以 `text/markdown; charset=utf-8` 返回，并禁止 MIME 嗅探；内容摘要通过响应头返回。渲染时不执行原始 HTML 或危险链接，代码块中的标记保持文本含义。

## 3. 无索引的笔记列表

列表按最近修改时间倒序，相同时间按笔记 ID 升序，为没有搜索的一期提供再次访问入口。本地模式列举 `notes/` 并以受限并发 stat 获取修改时间；OSS 模式遍历 ListObjectsV2 的所有页，使用 Key、LastModified 和 Size，不额外读取正文来排序。排序后仅为当前页读取最多 8 KiB 的开头片段取得标题，片段读取并发初始上限为 4。

API 游标编码最后一项的修改时间和 ID，不直接透传 OSS 的 Key 游标。每页请求重新列举元数据、排序并选择游标之后的内容，不缓存或落盘全库清单。并发增删改时允许非快照分页，新修改可能移动到前页；显式刷新回到第一页，当前页期间删除的文件跳过。客户端合并分页时按 ID 去重。

列表加载不阻塞编辑器可输入，且不随正文每 5 s 的轮询刷新。服务启动不扫描全部正文。此设计明确接受 O(N) 的元数据扫描：OSS 每次最多列举 1,000 项，10,000 篇至少需要约 10 页元数据请求，另有当前页片段读取；本地有 N 次 stat。实际请求数、耗时和字节数都纳入验收，不预先断言扫描成本更低。[OSS ListObjectsV2](https://www.alibabacloud.com/help/en/oss/developer-reference/listobjectsv2)。

## 4. 条件读取与有界校验缓存

应用对外的 ETag 始终是正文 SHA-256；OSS 原生 ETag 仅作为变更探测信号，不等同于此摘要。维护最多 128 项、闲置 30 分钟淘汰的 LRU 内存映射：noteId → 存储元数据与 SHA-256。只在实际读取时填充，不持久化、不全库预热，重启后为空。

- OSS 对已缓存笔记先调用 HeadObject，比较原生 ETag、LastModified、Content-Length；三者未变、无待确认写入且客户端 If-None-Match 等于已验证 SHA-256 时返回 304。HeadObject 不返回正文。[官方说明](https://www.alibabacloud.com/help/en/oss/developer-reference/headobject)。
- 冷启动、淘汰、元数据改变或客户端需要正文时完整 GetObject 一次，以该次响应自身的元数据和实际字节计算摘要、更新映射，不能混用先前 HEAD 的元数据。客户端摘要匹配则返回 304，否则返回正文；没有客户端摘要的普通读取可以直接 GET，不先做 HEAD。
- 本地模式使用 stat 的 inode、size、mtimeNs、ctimeNs 探测；无法获得可靠元数据时退回完整读取。两种模式都只支持本实例修改正文，不支持绕过应用直接编辑存储。
- 探测、完整读取及映射更新与该笔记写入由同一串行协调器保护，避免旧 GET 在新写入后回填旧映射。开始修改就移除旧映射，成功后可用本次确认的内容与存储元数据重建；缺少元数据则留待下一次读取。
- HEAD/stat 失败不能当作未修改，需返回错误；待确认写入移除缓存，恢复核对必须实际读取，不能用缓存或 304 放行。并发条件读取可以合并同一在途探测，但不引入额外的时间缓存拖延多端发现变化。

5 s 轮询仍会产生请求费用，只避免重复下载未变正文。以单页、单笔记、无编辑和无其他请求为基准，缓存热后主动执行 12 次条件检查，应得到 12 次 HEAD、0 次完整 GET、0 正文字节；重启后的第一轮至多增加一次完整 GET，此后恢复该模式。验收分别记录冷、热、变更和淘汰后的请求计数；部署说明列明每个持续前台页面约每分钟 12 次探测请求。

## 5. 当前文件提交

存储层只暴露列举、读取、创建、替换和删除。应用层按 noteId 串行执行修改，对实际保存的 UTF-8 字节计算 SHA-256 作为当前内容校验标识；不把摘要写入笔记内容。HTTP API 可以使用 If-Match，但这是应用负责校验的协议，不直接假设 OSS 支持条件覆盖。

- 新建与更新是不同操作；更新目标不存在时返回明确错误，不能自动重建已删除的笔记。
- 替换前检查客户端读取时的校验标识，冲突时保留客户端草稿，由用户处理。
- 每次提交固定目标内容及其摘要，操作标识只出现在协议或部署侧待确认状态中。相同内容无需重复写入；当前文件匹配目标摘要时可以确认目标内容已保存，不据此声称拥有历史操作记录。
- 若当前文件已被其他提交替换，无法靠当前文件证明更早请求的全部历史。此时重新核对并报告冲突，不承诺跨任意时间的历史幂等结果。
- 同一笔记前一次请求未确认时，不发送后继内容；请求中途的新输入留在浏览器当前草稿。

这些提交信息与用户内容分离，不保存旧正文，也不建立版本目录。

### 本地文件

同一文件系统内写入临时文件并同步，完成后原子替换当前文件，再同步父目录；新建使用不覆盖已存在目标的发布方式。异常时不能暴露半写文件或提前返回成功。临时文件是未完成写入，不作为历史副本保留。

发布前的校验与替换由同一应用实例中的笔记写入队列保护。只支持经过验证的本地文件系统，部署时不允许两个实例共同修改数据目录。[Node.js 文件操作](https://nodejs.org/docs/latest-v24.x/api/fs.html)。

### OSS

直接读取和覆盖 `notes/<note-id>.md`。OSS 的单对象操作具有原子性和强一致性，但普通 PutObject 不支持 If-Match 条件覆盖；并发检查由唯一 Node.js 写入入口和每篇笔记的串行队列完成。[OSS 一致性](https://www.alibabacloud.com/help/en/oss/user-guide/what-is-oss)、[OSS 条件上传限制](https://help.aliyun.com/zh/oss/user-guide/0017-00000245)。

发起创建、覆盖或删除前，先持久化部署侧最小待确认记录；正常写入完成后返回保存成功并清理记录。写入超时必须进入“结果待确认”：保留浏览器草稿和记录，暂停同一笔记的后续修改，读回完整文件计算摘要或核对删除目标。记录包含操作类型、请求标识、原摘要和目标摘要，不保存正文，也不插入 Markdown 文件。

修改请求关闭 SDK 和代理的自动重放，避免迟到的旧请求覆盖新内容。读回本次提交可以确认成功；读到旧内容不等于旧请求已经终止，不能据此立即放行后继写入。重启后仍要处理未确认请求，不能丢弃状态后继续覆盖。无法确认结果时保持阻塞并明确反馈，不虚报失败或成功；这是 OSS 适配需要真实故障测试的边界。

Bucket/前缀由应用独占写入，一期不启用应用管理的对象版本功能；所选部署配置应避免自动生成历史对象。此方案不依赖禁止覆盖请求头构造版本日志，也不把对象存储当作支持多对象事务的数据库。

### 状态卷绑定与启动检查

OSS 正文仍只在 `notes/`，另外保留唯一的 `control/state-owner` 部署身份标记，不是笔记索引、备份或版本。它绑定本地状态卷中的随机 `stateId` 和 Bucket/前缀，不能包含密码、密钥或正文。

1. 首次部署显式运行初始化，确认笔记前缀为空且远端标记不存在；先将随机身份写入本地卷并同步文件与目录，再用 `x-oss-forbid-overwrite: true` 的 PutObject 创建远端标记，并读回核对。此请求头在版本启用或暂停的 Bucket 中不生效，因此初始化与启动都必须确认 Bucket 未启用版本功能，Enabled、Suspended 或无法读取状态均拒绝启动。该标记不构造逐次版本对象。[PutObject 请求头](https://www.alibabacloud.com/help/en/oss/developer-reference/putobject)。
2. 初始化响应不明时只读回核对，不自动覆盖或换一个身份重试；本地身份已落盘、远端标记尚不存在且笔记前缀仍为空时，重新显式执行初始化可以使用原身份继续。正常服务启动不创建或修补标记。
3. 每次启动先核对本地身份、远端标记、配置中的 Bucket/前缀及待确认记录格式，再开放笔记写入。任一缺失、不匹配、读失败或记录损坏均拒绝启动。远端已初始化而本地为空时，不允许拉取身份标记后创建空记录目录来继续写。
4. 初始化和正常启动均检查状态目录。容器使用专用 bind mount / named volume；Linux 拒绝已知 tmpfs / ramfs，提供的容器还要求状态路径为独立挂载点，缺失挂载不能落到容器可写层。写入、fsync、回读探针仅检查当下可写；防止重启后的空卷被当成新部署依赖上述双端身份校验。

状态卷丢失或错挂后提示挂回原卷，在此之前保持拒绝写入；不能提供清空待确认状态的自动恢复开关。此检查不声称能够检测任意磁盘故障或人为回滚、克隆状态卷的旧快照；部署约束禁止运行中复制、回滚或手工修改状态目录。验收必须包含状态卷正常重启、整体丢失、换卷、tmpfs、容器遗漏挂载和初始化中断。

## 6. 后续扩展预留

笔记 ID 保持稳定，文件读写集中在存储适配器中。以后增加历史功能时，可以新增独立历史目录或对象前缀，将每次历史内容保存为独立文件。

MVP 不创建该目录，不复制旧内容，不加入历史记录、恢复或备份流程。当前只验证单篇当前内容的正确读写和多端冲突提示。
