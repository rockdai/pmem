# task-090：Personal Memory 一期 MVP 实现规格

状态：待评审，尚未开始产品代码实现。日期：2026-09-23。

本规格承接 `docs/mvp-architecture` 分支的 `0da9183673b00501696a6f075a2da7770845cf84`，并将该分支的架构文档纳入本任务。遵循已确认的顺序：先评审方案，通过后再编码。本文件是本任务的实现与验收入口；下文明确的约定补充架构提案，未改变的部分继续采用提案。

## 1. 目标与交付范围

完成一个可自托管的个人在线记事本：一个部署、一个账号、本人多设备使用。用户可以登录、浏览笔记、新建、打开、富文本编辑、自动保存、删除，并在另一台设备继续记录。

打开快和多端体验是硬要求。速度衡量到“正确内容已就绪，能输入且能保存草稿”，不以出现界面代替。服务端采用 Node.js；正文只能存入本地文件或 OSS 中的一种。

一期不实现搜索、服务端持久化或全库笔记索引、备份、历史版本、多人协作、附件上传、表格、数据库视图或完整 Notion 功能。允许有界、按访问建立、随进程结束丢弃的内容校验缓存，不能用于搜索或维护全库目录。保留稳定笔记 ID 和存储适配器即可，不预建历史目录或版本表。

## 2. 技术栈与代码边界

以 TypeScript、pnpm workspace 和 Node.js 24 系列为基线。[架构提案](../architecture/phase-1.md) 中的 React / Vite、Fastify、Dexie、Tiptap / ProseMirror 与 Markdown 转换库是候选，须通过原型后确定；浏览器草稿持久化采用 IndexedDB，不强制使用其 Dexie 封装。实现时确认依赖兼容性并提交 lockfile，不使用浮动安装结果作为验收环境。

建议最小目录如下，不为后续知识库功能预建模块：

```text
apps/web/              # 页面、编辑器、当前草稿、保存状态
apps/server/           # 认证、HTTP API、写入协调、本地与 OSS 适配器
packages/contracts/   # ID、接口类型、错误码与大小限制
tests/e2e/             # 浏览器中的记录、恢复和多端行为
docs/                  # 设计、部署说明与实际验收记录
```

Web 和 API 同源部署。一个活动 Node.js 实例负责所有设备读写，不支持多个进程或副本同时操作同一存储。服务端凭据不下发浏览器。

## 3. 内容格式与编辑范围

本任务推荐采用 UTF-8 Markdown，存储路径为 `notes/<note-id>.md`。Markdown 标记表达内容格式，不存页面 HTML、CSS、JSON 外壳、front matter、标题副本、编辑器内部模型或隐藏提交标记。正文以 `text/markdown; charset=utf-8` 直接传输；服务端保留收到的 UTF-8 字节，不执行 Markdown 转换。

标题由内容首个非空行派生。列表只读取每篇笔记前 8 KiB，去除展示用的 Markdown 标记后截断标题；片段内无有效标题则显示“未命名笔记”。正文初始上限为 1 MiB，超限明确拒绝，不能截断保存。ID 使用客户端生成的随机 UUID，服务端严格校验格式，不能把任意客户端路径传给存储层。

可视化编辑开放段落、标题、粗体、斜体、链接、有序与无序列表、任务列表、引用和基础代码块；提供工具栏、常用快捷键及简单斜杠菜单。界面自适应桌面与手机宽度，输入时不因列表刷新而重建编辑器。

点击“新建”只分配本地 ID、创建空白编辑区，不立即发 POST 或创建远端空文件。首次出现非空白文字或非空代码块内容后才进入创建保存队列；中文输入等待组合输入结束。只有空段落、空列表、空任务项或纯格式操作不触发创建。发出 POST 前又清空时取消尚未发送的创建并回收空草稿；一旦 POST 已发出，就按创建结果确认协议处理，不能假定取消成功。已确认的笔记清空后仍保留一个空内容文件，只有明确删除才移除。

Markdown 往返按以下边界验收：

- 支持的块结构、强调范围、任务状态、链接目标、中文字符及代码块文本保持语义一致；不要求 Markdown 标记写法或无意义空白逐字一致。
- 普通段落分隔使用空行，段内显式换行导出为行末两个空格加换行，读取时也接受反斜杠加换行；连续空段落规范化为一个段落间隔。代码块内部的空格、空行和换行不得参与此规范化。
- 打开笔记、获得焦点和读取内容均不触发重写。只在用户实际编辑后生成保存内容。
- 编辑器不能表达的输入不得静默丢失。粘贴内容只转换支持的格式，其余呈现为可见文本；发现存量文件不能安全往返时保留原文，提供纯文本查看、复制和明确提示，不自动覆盖文件。
- 用户输入的 HTML 片段是内容，按文本展示或保留在代码块中，不执行，也不由应用生成 HTML 包装保存。可点击链接仅允许 `https:`、`http:` 和 `mailto:`，其他协议按文本展示。

先完成编辑器内容往返与正式构建体积原型，再扩展页面。若候选转换器无法通过上述用例或体积预算，需要调整选型并更新本规格，不能以隐式丢失内容或降低硬指标过关。

## 4. 服务端接口与保存一致性

接口沿用 [API 草案](../architecture/phase-1.md#7-api-草案)，补充以下实现约定：

| 操作 | 约定 |
| --- | --- |
| 登录、会话、退出 | 所有正文及列表接口均要求有效会话；未登录返回 401 |
| `GET /api/v1/notes` | 默认每页 20 篇，最多 50 篇；按存储修改时间倒序、相同时间按 ID 升序，使用不透明游标 |
| `GET /api/v1/notes/:id` | 返回原始正文及 SHA-256 内容摘要对应的 ETag；支持条件读取；不存在返回 404 |
| `POST /api/v1/notes/:id` | 仅新建，成功返回 201 和 ETag；已存在返回 409，不覆盖 |
| `PUT /api/v1/notes/:id` | 必须携带读取时的 If-Match；成功返回当前 ETag；不能隐式新建 |
| `DELETE /api/v1/notes/:id` | 必须携带当前 If-Match；成功返回 204 |
| 前置条件与输入错误 | 缺少 If-Match 返回 428，摘要不匹配返回 412，目标不存在返回 404，正文超限返回 413，非法 ID 返回 400 |
| 存储结果待确认 | 返回可识别的 503 错误码 `write_pending`；客户端保留草稿，不继续自动写同一笔记 |

登录、列表和错误等控制信息可以使用 JSON；禁止的是用 JSON 封装笔记正文，不是为少量控制信息另造协议。正文响应禁止 MIME 嗅探，认证 API 不允许共享缓存保存私人内容。

按 noteId 串行化创建、更新和删除，前置条件检查与写入属于同一个临界区。摘要只描述当前内容，不是历史版本号，不承诺检测内容恢复到相同字节之前发生过的所有操作。写请求完成只确认那一次提交，不能将随后输入一并标为已同步。

新建和更新保持不同的客户端状态：远端确认存在后只发更新。写请求结果未知时先读取核对，不能无条件自动重放。尤其是创建响应丢失后读到 404，无法区分“从未创建”和“已创建又被删除”，此时保留草稿并提示用户处理；需要另存时使用新 ID，不自动重建原 ID。

### 再次访问与条件读取

主页明确提供“最近修改”笔记列表；同一浏览器记住最后打开的笔记 ID，再次进入时优先恢复该笔记，已删除则回到列表并保留其未同步草稿。新设备登录后从最近修改列表进入笔记，不依赖本地最近访问记录。最后打开的 ID 是浏览器 UI 状态，不写入正文。

列表每次请求列举全库的文件元数据后排序，本地为文件名及 stat，OSS 为 ListObjectsV2 的 Key、LastModified 和 Size；只读当前页最多 50 个正文开头片段。游标编码最后一项的修改时间和 ID，后续请求重新列举并筛选其后项；并发增删改不保证快照一致性，刷新从第一页重新获取。此方案接受元数据扫描成本，禁止扫描全库正文或落盘索引。列表仅在打开列表、显式刷新或本机增删改完成时按需刷新，不跟随正文的 5 s 轮询扫描全库。

正文条件检查采用 [存储设计中的探测与缓存协议](../architecture/storage.md#4-条件读取与有界校验缓存)：OSS 先 HEAD 探测原生元数据，命中进程内摘要映射、文件未变且客户端摘要相同时返回 304；缓存冷启动、淘汰、对象变更或客户端需要正文时完整 GET 并计算 SHA-256。缓存最多 128 项，闲置 30 分钟淘汰；不扫描预热、不持久化。自身写入使旧映射失效；待确认写入的核对必须绕过缓存。重启或淘汰只增加下一次读取成本，不改变正确性。

### 本地模式

正文仅位于配置的数据目录。采用同文件系统临时写入、文件同步、原子发布与父目录同步；新建不能覆盖同名目标。拒绝路径穿越和符号链接越界，临时文件不参与列表，启动时仅清理能安全判定的未完成临时写入。发布或同步失败不能报保存成功。

### OSS 模式

正文仅位于专用 Bucket/前缀，直接列举并按需读取，不建立目录清单。本实例是该前缀的唯一写入方；不得假定普通 OSS 覆盖请求具有应用所需的条件更新能力。具体依据见 [存储设计](../architecture/storage.md)。

每次创建、覆盖或删除在发往 OSS 前，先持久化最小待确认记录，包含 noteId、操作类型、请求标识、原摘要及目标摘要或删除目标；不保存正文。关闭修改请求的 SDK 自动重试。正常确认后清理记录；响应丢失时暂停该笔记后续修改，通过读回当前完整内容或确认不存在来核对目标。

读到旧内容不能证明原请求已经终止；结果仍不明确时保持暂停、保留浏览器草稿，并允许复制或以新 ID 另存。重启后先恢复这些待确认记录，再接受对应笔记的新修改。不得通过清空记录自动解除阻塞。实现必须用故障注入验证“延迟的旧写入不能覆盖后续内容”。

OSS 模式因此需要持久化的部署状态目录，保存配置和少量待确认元数据，不是本地正文副本或第二个笔记存储。首次初始化将本地状态卷身份与 OSS `control/state-owner` 标记绑定；后续启动只校验，缺失或不匹配就拒绝启动，不能从远端标记自动重建空卷。初始化仅适用于空的笔记前缀，使用不覆盖的标记创建；具体初始化中断、错挂卷和持久化校验见 [存储设计](../architecture/storage.md#状态卷绑定与启动检查)。此项部署要求及无法确认时的暂停行为必须写入部署说明。

## 5. 浏览器草稿与多端交互

### 草稿槽位生命周期

浏览器保存当前草稿、读取基准摘要以及尚未确认的提交状态；不积累草稿历史。按部署身份、笔记 ID、标签页槽位隔离，生命周期如下：

- 槽位 ID 为随机 UUID，放在 sessionStorage 中以便刷新复用；页面持有该槽位的独占 Web Lock 才能写入。使用 `ifAvailable` 非阻塞取得锁，不使用 `steal`；复制标签页导致 ID 重复时，未取得锁的新页面重新分配 ID，不写原槽位。不支持 Web Locks 时每次页面加载都分配新 ID，旧草稿通过恢复入口处理。[Web Locks 说明](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API)。
- 远端确认且没有更新的本地输入时，在 IndexedDB 事务中校验草稿修订号，删除该槽位的待同步记录；另存每篇笔记最多一份干净内容缓存供暖启动，缓存不是历史或待恢复草稿。新的输入重新建立当前槽位记录。
- 未发送创建的空草稿可立即清理；已同步残留记录在下次启动时清理。关闭事件只用于尽力清理，不依赖它保存内容；崩溃或直接关闭后的未同步内容持续保留，不按时间或数量自动删除。
- 恢复入口按最后编辑时间倒序，每页展示 5 份并显示总数和“加载更多”；存在多个草稿时用非阻塞提示进入选择，不反复弹出全量选择框。未同步草稿不设会导致数据丢失的数量上限，浏览器容量失败按保存失败处理。
- 恢复到当前槽位并完成本机持久化后，仅在取得原槽位锁且确认修订号未变时移除原记录；仍被其他标签使用的草稿只能复制，不移除。不支持 Web Locks 时不自动回收未同步原记录，恢复后仍可明确丢弃。成功同步或用户明确丢弃是未同步草稿的回收路径。

输入变化进入有序的 IndexedDB 保存队列；本机保存完成后显示“已保存到本机，待同步”。远端采用 500 ms 防抖、持续输入最多 2 s 提交一次，每篇笔记最多一个请求在途。旧响应不能覆盖新输入，也不能将新输入标记为已同步。中文组合输入期间不替换编辑器内容，不触发会破坏选区的格式转换。

### 保存拒绝与恢复

客户端在排入远端提交前按实际 Markdown 的 UTF-8 字节数检查 1 MiB 上限；检查失败仍尝试保存完整本机草稿，不截断、不发送。服务端继续独立校验，不能信任客户端的检查。

| 结果 | 客户端状态与恢复 |
| --- | --- |
| 本机预检超限或服务端 413 | 显示“内容超过 1 MiB，暂不能同步”及真实的本机保存状态；取消该内容的远端计时器和重试；可缩减、复制或手动拆为新笔记，重新降到上限内后才恢复自动保存 |
| 400 非法 ID / 请求，或其他不可重试的输入错误 | 显示“无法保存，可复制内容或另存为新笔记”，保留草稿，停止该操作自动重试；修正请求或用户明确另存新 ID 后才恢复，刷新不能重发同一无效提交 |
| 401 | 保留草稿，暂停远端提交，重新登录并核对远端后恢复 |
| 412，或更新/删除时 404 | 标记冲突或已删除；保留草稿，用户选择处理，不自动新建原 ID |
| 创建时 409 | 读取目标核对；与待创建内容一致可转入已存在状态，否则提示冲突，不覆盖 |
| `write_pending` 或写请求超时、连接中断 | 进入结果待确认，只读核对，禁止盲目重放或发送后继提交；不能以 GET 304 作为待确认写入已完成的证明 |

以上阻止提交的原因随当前草稿持久化，页面刷新后先重新校验，不被保存防抖绕过。是否“已保存到本机”独立取决于 IndexedDB 是否成功；本机失败时明确未持久化并保留内存内容供复制。

打开和恢复前台时检查远端，可见页面每 5 s 条件检查当前笔记。无本地修改时可以应用新内容；存在本地修改、在途保存或组合输入时不替换正文，进入待处理状态。冲突提示允许保留当前草稿、查看远端内容、复制或以新 ID 另存；丢弃草稿需要用户明确选择。

身份验证与笔记列表独立于编辑器资源加载。首次访问及未缓存笔记需要联网；会话确认后可先恢复本地内容，列表不阻塞输入。已打开页面断网仍保存草稿；一期不承诺断网冷启动。会话过期时保留草稿、停止远端写入，重新登录后先核对远端再恢复保存。

退出前处理未同步内容，不能先清空草稿再提示；明确退出后清理账号草稿与缓存。IndexedDB 不可用或空间不足时，界面显示未持久化状态并保留内存内容供复制，不虚报“已保存”。

## 6. 认证与部署交付

仅有部署时配置的个人账号，不开放注册。沿用架构提案的密码哈希和加密 Cookie 会话，实施登录限流、Origin / CSRF 校验及安全 Cookie 属性。为使修改密码后旧会话失效，启动时计算 `authBinding = HMAC-SHA256(sessionKey, "pmem-auth-v1\0" + account + "\0" + PASSWORD_HASH)`；登录成功时写入加密会话，所有受保护接口每次校验其与当前值相同，不匹配或缺失返回 401 并清除 Cookie。不能自动给旧会话补上新值。更改密码哈希并重启后，即使会话密钥不变，旧 Cookie 也不能继续使用；仍保留原有会话到期检查，不建立会话数据库。插件只提供载荷保存和加解密，绑定校验由应用负责。[插件官方文档](https://github.com/fastify/fastify-secure-session)。

自托管公开访问使用 HTTPS，开发模式的本地 HTTP 配置不得成为生产默认值。提供的 OSS 容器部署必须将状态目录独立挂载到持久卷，启动拒绝 tmpfs / ramfs 及缺失的独立卷挂载；写入、同步并回读探针只能证明当前可写，不能证明重启持久性，仍须校验卷身份绑定。

交付一份多阶段构建的 Linux 容器、配置示例和可复制的部署步骤。必填配置包括账号、密码哈希、会话密钥、外部访问 Origin、存储模式及其目录或 OSS 参数。启动时验证所选模式的必要配置；OSS 凭据、会话密钥、密码和正文不得进入日志、镜像或提交记录。

本地与 OSS 模式使用同一应用接口且二选一，不实现运行中的存储切换、数据迁移或双写。部署说明明确单实例限制、卷权限、待确认状态卷和正文 1 MiB 边界。

## 7. 验证与通过标准

性能目标沿用 [性能与多端验收](../architecture/performance.md)，均是待验证门槛，不是已有成绩：冷打开 P95 桌面 1.5 s / 手机 2.5 s，暖打开 500 ms / 800 ms，初始必需 JavaScript 合计 250 KiB gzip，CSS 30 KiB gzip。验收必须包括 Markdown 转换、编辑器初始化及草稿保存链路。

| 层次 | 必须取得的证据 |
| --- | --- |
| 编辑器原型 | 支持的格式、中文、代码空白与换行往返；不支持内容不会被静默覆盖；正式构建资源清单 |
| 服务端与本地存储 | 认证和前置条件；只改密码哈希重启后旧 Cookie 被拒绝、新登录成功；并发提交、创建/删除/旧请求交错、路径边界、磁盘满和原子发布失败 |
| OSS 适配器 | 相同接口契约、真实 Bucket 读写、响应丢失、迟到写入、进程重启和待确认记录恢复；缓存热/冷/淘汰/写入失效及 HEAD 失败，不用旧缓存返回 304 |
| 浏览器端到端 | 登录至记录、保存期间继续输入、刷新与崩溃恢复、复制标签页、已同步槽位回收、草稿分页；首次有内容才创建；2 MiB 粘贴/服务端 413/400 不重复提交、缩减后恢复；冲突、删除后旧编辑、会话过期和本地存储失败 |
| 多端与性能 | 新设备能从最近修改列表找到刚编辑的笔记；10,000 篇元数据扫描、分页与同时间排序；生产构建、标准/弱网、至少 30 次样本及 P50/P95/失败数；正文轮询的 HEAD/GET 次数和实际字节数 |
| 自托管 | 本地与 OSS 分别部署；正常重启、状态卷丢失/错挂/tmpfs/缺失挂载及初始化中断；远端已有身份标记时空卷启动失败且不发生笔记修改 |

单元测试和 Mock 成功不能代替真实 OSS 与手机验证。缺少测试 Bucket 或手机时，报告可执行的检查步骤与尚未验证项目，不声称功能或硬指标全部验收通过。

## 8. 实施顺序与评审交付

1. 本阶段提交规格和关联架构文档，发布方案 PR，交由 QA 评审；不提交产品实现。
2. 方案通过后，先做候选编辑器与 Markdown 的正式构建原型。统计所有首字输入前的代码，包括路由、转换器和 IndexedDB 封装；若超预算，依次裁掉非必需扩展与依赖、简化路由/改用原生 IndexedDB、替换 Tiptap 封装或 Markdown 转换器，再考虑 Web 框架替换。每步重测往返和体积，保留已承诺功能、持久化及速度要求；仍不能通过时更新方案交 QA 复核，不扩大到完整实现或抬高预算。
3. 完成本地模式的登录、列表、编辑、自动保存、删除闭环及浏览器草稿恢复。
4. 完成 OSS 模式和多端冲突、异常保存用例，再完成生产构建、部署与性能验收。
5. 更新 README 和验收记录，写清真实通过项、未验证项及已知限制，提交实现供代码评审。

QA 本轮重点判断范围是否符合已确认需求、Markdown 可视化编辑是否可验证、无数据库与无历史存储下的失败处理是否可实现，以及性能验收能否反映实际“打开就能记”的体验。
